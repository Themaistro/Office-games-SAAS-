# Security and scaling remediation — 10 November 2026

This implements the local code changes identified in the [architecture/security audit](architecture-security-scale-audit-2026-11-10.md). It is not a hosted rollout or a penetration-test certificate. Existing player accounts/passwords and gameplay records are preserved.

## Verification

- Formatting, lint, TypeScript, architecture and gameplay/content/recovery checks passed.
- Full database verification passed with the restricted runtime credential: 50 owned tables, 55 foreign keys, mission configuration, match/rematch/invitation/party regressions and failure cleanup.
- New contracts cover malformed/file form fields, Unicode password bounds, URL validation, spoofed/missing origins, throttling, inactive/orphan identities, newest activity, polling coalescing/visibility/unmount behavior and transaction rollback/commit failures.
- Database tests cover concurrent attempt budgets/reset, session caps/cookie settings, deactivation/revival, administrator reauthentication, concurrent expiry with inactive players and timeout recovery.
- Production build and fresh-database bootstrap/repeated migrations/restricted-role checks passed.
- Real HTTP tests passed for actual login action/cookie issuance, malformed login form handling, player/admin authorization, private invitations, spectators, messaging/read-receipt ownership and valid/invalid write origins. The bounded workload completed 1,125 requests with zero errors; observed p95 at 50 concurrent clients was approximately 68–86 ms across runs (including a run alongside the fresh-database rehearsal). This is not a full realtime or move-latency workload.
- A temporary 19,000-row history fixture produced the same newest 30 activity IDs. Runs observed approximately 27–34 ms for the unbounded merge versus 0.34–3.1 ms with bounded sources. The script saves its actual plan/timing in ignored `output/activity-history-plan.json` and rolls back all fixture data. Timings vary; this is not a universal speed guarantee.

## Operator notes

Migrations 33 and 34 were applied locally. Existing applied migrations were not rewritten. Migration 34 replaces only newly added feed indexes to match the verified sort order; review index-build locking and installation size before any hosted rollout. Re-run runtime-role provisioning when adding tables to an existing installation.

`npm run db:migrate -- --local` loads runtime local configuration and then the optional operator-only `.env.migrations.local`. Fresh-database rehearsal also uses that operator connection to create/drop its isolated database. Normal application tests continue to use the runtime role. Hosted migration credentials must live in deployment tooling, not the application environment.

Registration mode defaults to open in development and invite-only in production unless explicitly configured. The example configuration is invite-only; a fresh local installation needs an explicit temporary `REGISTRATION_MODE=open` to create its first account. New-password minimum defaults to six in development and twelve in production; existing test passwords are unchanged. The example uses twelve. Open registration does not claim email ownership; email delivery/verification is not implemented here. Invitation acceptance remains email-bound and single-use.

The API origin policy is for the current cookie-authenticated browser APIs. Future webhooks or server clients need explicit authenticated routes/policies rather than broadly disabling this check. Trusted reverse proxies must preserve the real Host/protocol; forwarded-host bypasses are not accepted.

Login budgets are ten account attempts per ten-minute fixed window and 300 company attempts per minute; registration is thirty company attempts and three per email per ten minutes. A correct login still counts toward its window. These are bounded throttles, not permanent account locks. Large installations should tune limits through a deliberate configuration change and load test, and use edge/network abuse controls too. PostgreSQL-backed throttling itself cannot protect against all network denial-of-service traffic.

Cleanup is bounded and opportunistic through shared database leases; invite validity never depends on a browser running physical cleanup. An always-on scheduled job can reuse the maintenance operations if traffic/retention requirements justify it. Durable background projections/outbox processing, cache infrastructure and microservices are not introduced speculatively.

## Remaining validation boundaries

All code changes are local. No GitHub push, Neon migration or Vercel deployment was performed. Hosted connection budgets, provider/pooler behavior, real multi-browser Ably disconnect/fan-out tests, prolonged mixed move/read/write workloads and production security testing remain separate tasks. They cannot be established by this local regression suite. Some generic legacy repositories and large UI components remain; the feature boundaries and tested workflows provide a basis for incremental cleanup rather than a claim of complete repository conversion.
